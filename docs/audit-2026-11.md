# Audit: technical, UI/UX, SEO and conversion — atikulislam.me

**Date:** 25 November 2026
**Repository:** `Atikulislamx/Atikulislamx.github.io` (branch `arena/77c67b88…`, base `2441744`)
**Live site:** <https://atikulislam.me> (GitHub Pages, `build_type: legacy` = Jekyll, deployed from `main`, last deploy 2026-10-08, HTTPS enforced, custom 404 active)
**Scope:** read-only audit. No code was rewritten. Every finding below is a diagnosis with a fix direction.

## 1. Verdict

The site is **well built but badly exposed**, and the gap between what it looks like (a credible security practice) and what an inspecting buyer finds (unfinished trust infrastructure) is the core problem.

- **Craft is genuinely good.** Valid HTML, one `<h1>` per page, correct heading order, no skipped levels, unique titles and descriptions, correct canonicals, per-page OG cards, a working custom 404, AA-contrast colour tokens (verified mathematically), visible focus rings, `prefers-reduced-motion`, content that survives JavaScript being off. Zero broken internal links, zero orphan pages, zero placeholder text.
- **But four things undermine everything else:** internal working documents are publicly readable; **all 79 structured-data blocks are invalid** (no `@context`); the desktop Services mega-menu opens off the right edge of the viewport; and there is no legal, pricing, proof or credential layer at all.
- **The measurement layer is empty.** GTM is installed but fires no events, has no consent gate, and the contact form has no conversion tracking. You cannot currently tell whether the site produces a single lead.
- **Strategic gap:** there is no content engine (`/blog/` 404s), so the site competes for high-intent queries ("recover a hacked Facebook page") with 20 thin brochure pages and no article to rank.

Priority counts: **6 critical · 13 high · 11 medium · 8 low.**

## 4. P0 — Critical

### P0-1 · Internal working documents are publicly readable ✅ verified live

`https://atikulislam.me/docs/audit-2026.md` returns the **full internal audit**, including the list of claims removed as unverifiable, the fact that client permission is unconfirmed, and the pending legal review. `https://atikulislam.me/README.md` returns the full repo guide. Also published: `RELEASE.md`, `docs/deployment-checklist.md` (**contains the Web3Forms access key in plain text and the pending O1–O6 to-dos**), `docs/asset-pipeline.md`, `design/og-template.html`, `scripts/*.js`, `data/*.json` (including `site.json → unverifiedClaims`), `package.json`, `package-lock.json`, and **26 files under `prompts/`** — 5,540 words of internal process.

**Why it matters.** This is the single most damaging finding. A prospective client researching a security professional can read that the practice's own audit says: *"Client names … published with no recorded permission"*, *"Legal review of the Dinajpur line"*, *"confirm the Web3Forms access key is active"*. It is also indexed by search engines (`robots.txt` allows everything) and makes the brand look careless about exactly the discipline it sells.

**Cause.** GitHub Pages runs a legacy Jekyll build and copies every file and folder that does not begin with `.` or `_`. There is no `_config.yml` and no publish scoping, so the repository root *is* the web root.

**Fix direction.** Scope what is published — either move `docs/`, `prompts/`, `scripts/`, `design/`, `data/`, `README.md`, `RELEASE.md` and `package*.json` to a Jekyll `exclude:` list in a committed `_config.yml`, or move the site into its own publish folder and switch Pages source to it. Add `robots.txt` `Disallow` lines as an immediate stopgap while the build is being changed. (Note: `.nojekyll` alone does **not** solve this — it disables Jekyll processing but still publishes every file.)

### P0-2 · Zero valid structured data — 79 blocks, 0 with `@context` ✅ verified in source

Every page emits JSON-LD as a bare object:

```json
{"@type":"WebSite","@id":"https://atikulislam.me/#website", … }
```

There is no `@context` anywhere in the repository (`grep -l '@context' --include=*.html .` → no files; 79/79 blocks missing it). Without `{"@context":"https://schema.org"}` the vocabulary is unbound, so none of the `@type`/property names have meaning to a parser.

**Impact.** Google's Rich Results Test will not produce a valid entity graph: no Organization/Person knowledge-panel signals, no Article enhancement, no breadcrumb, no Service understanding. The work invested in a well-modelled `Service`/`Article`/`ProfilePage` set currently returns nothing. It also contradicts `docs/audit-2026.md` H12 ("One consistent `@graph` per page") — there is no `@graph`.

**Fix direction.** Emit one `<script type="application/ld+json">` per page containing `{"@context":"https://schema.org","@graph":[…]}` with the existing nodes as members, and add a checker rule that fails when `@context` is absent (this is the rule that would have caught it). Validate with the Rich Results Test and Schema Markup Validator on `/`, a service page, a case study and `/faq/`.

### P0-3 · Defamation risk in the Dinajpur case study ✅ verified live

`/case-studies/dinajpur-image/` → *"The page was disabled after the reports. The reporting party allegedly demanded money in connection with them."*

**Impact.** This publicly attributes attempted extortion to a partly identifiable counterparty in a live commercial dispute. "Allegedly" mitigates but does not remove the exposure, and it is a reputational liability for a business that asks clients to share sensitive account evidence. The prior audit logged this as "High / needs legal review"; given the doc itself says the review has not happened, it belongs at Critical until it does.

**Fix direction.** Remove the sentence, or reduce to a neutral statement ("the reports were contested") until a lawyer signs off in writing.

### P0-4 · No legal layer, and tracking without consent ✅ verified in source

- No `/privacy/`, `/terms/`, `/refund/` or `/disclaimer/` page exists. "Privacy" appears only as an FAQ category label (4 pages) and "terms" only inside the trademark sentence.
- The contact form collects name, email, service and free-text (which will contain incident details) and posts it to **Web3Forms** in the US. The form and FAQ describe *that it happens* but there is no policy covering retention, rights, or the processor.
- **GTM-PHVGHCMT is injected into all 21 pages with no consent gate**, no cookie banner and no CMP. It almost certainly loads GA4 (an ad-tech cookie set) for EU/UK visitors.

**Impact.** GDPR/ePrivacy exposure for a business that explicitly sells to "worldwide" clients, plus a credibility problem: a security practice asking for hacked-account details has no stated data-handling policy, and visitors are tracked before consenting.

**Fix direction.** Publish privacy (processing purposes, retention, third processors: Web3Forms, Google), terms, and a scope/refund policy; link them from the footer, the form and the success message. Gate GTM behind a consent decision (or drop GA4 for a cookieless analytics tool). Enable Cloudflare Email Routing/Workspace so `help@atikulislam.me` exists as a policy contact.

### P0-5 · `/blog/` and legacy `/Atikulislamx/` are dead ends ✅ verified live

- `/blog/` → **404**. There is no `blog/` directory, no sitemap entry, no internal link. The only trace in the repo is `prompts/empty-states/empty-blog.json` ("Blog hub, pre-launch/empty state") — a plan that was never built.
- `/Atikulislamx/` → **404**. Legacy/project-site URLs and case-variant links (e.g. `AtikulislamX`) have no redirect.
- GitHub Pages cannot issue server-side redirects, so nothing catches either case.

**Impact.** Any external link or bookmark pointing at those paths (old portfolio links, social bios, forum posts) silently loses the visitor, and brand searches for "atikulislam blog" land on a generic 404 with no explanation.

**Fix direction.** Decide the content plan first: either ship a real `/blog/` hub (highest-leverage SEO move — see P1-5), or publish a small `/blog/` stub that explains the state and links to case studies. For legacy paths, add lightweight HTML redirect stubs (meta refresh + canonical + `<link rel="canonical">` to the target) or, better, front the site with Cloudflare and use a single redirect rule set — which also solves P1-8 and the caching limits in P1-7.

### P0-6 · The analytics layer measures nothing ✅ verified in source

`grep 'dataLayer\|gtag('` across `js/` → **no matches**. The form's success path (`showSuccess`) pushes no event, there is no thank-you page, and no virtual pageview or submit event exists. GTM is present on 21 pages and never reports a conversion.

**Impact.** You cannot tell whether the site generates leads, which service page converts, or whether the GTM container earns its ~110–160 KB. Combined with no consent (P0-4), you carry the cost and the legal exposure of tracking and receive none of the benefit.

**Fix direction.** Define one conversion event (form submit) and one micro-conversion (WhatsApp/email click), push them to `dataLayer`, and mark the form event as a GA4 key event. Consider replacing GA4 with a lightweight cookieless tool; if you keep GTM, add consent mode.

## 5. P1 — High

### P1-1 · The desktop Services mega-menu opens off-screen ◐ (high confidence, confirm in a browser)

```css
.submenu { position: absolute; left: calc(var(--space-4) * -1);
           width: min(760px, 86vw); }   /* no right constraint */
```

The panel is anchored to the **Services** nav item, which sits in the right-hand half of a 1200 px container (`.container-max: 1200px`, header padding 32 px, nav right-aligned). At 1440 px the Services item starts around x ≈ 926, so the panel spans 910 → 1670 — **~230 px past the viewport**. At 1024 px the overrun is ~350 px. Nothing clips it: neither `html`, `body`, `.site-header`, `.container` nor `.site-header__inner` sets `overflow`. It fits only above ~1920 px.

**Impact.** The third column — **Security Consultation** and **Social Media Security Audit**, two of your eight revenue pages — is rendered outside the viewport whenever the menu opens. Because the overflowing box is `position: absolute` inside a `sticky` header with no horizontal scroll container, opening it also introduces a page-level horizontal scrollbar and an unstable hover target. The previous audit's "verified by reading the CSS only" note is exactly where this slipped through; its "no horizontal scroll at 9 widths" test ran with the menu closed.

**Fix direction.** Right-align or centre the panel (`right: 0; left: auto`, or centre under the container) and clamp the width to `min(760px, calc(100vw - 2 * var(--space-4)))`. Then test the open state at 1024, 1280, 1440 and 1920.

### P1-2 · Zero social proof — and an unused Google Business Profile

Site-wide: **0** occurrences of testimonial/review-quote/client logo/award/press. Meanwhile `data/site.json` contains `"googleProfile": "https://g.co/kgs/RUh5c5i"` which is **linked from no page** and **absent from `Person.sameAs`** and from any schema.

That is the cheapest authority asset you own, unplugged: a verified Google Business Profile with reviews would (a) put star ratings in search results next to the brand, (b) give the entity graph a corroborating source, (c) provide third-party proof that does not depend on client confidentiality.

**Fix direction.** Link the profile in the footer and `sameAs`, add `ProfessionalService` fields (P2-9), and build a *permission-based* proof section: anonymised quotes with client type and scale ("Page owner, 400k+ followers, Bangladesh"), the public video the Zero Idea owner already shared (see P1-5), and Upwork/LinkedIn endorsements surfaced as text rather than a bare link.

### P1-3 · No price, package or scope signal anywhere

**0** occurrences of price/pricing/package/rate/budget/"starting at" across 22 pages. The only CTA is "Describe your situation".

**Impact.** Recovery buyers are in crisis, comparing 3–5 providers in an hour, and the first question is "can I afford this and what do I get?" With no signal, you get two bad outcomes: unqualified enquiries you must triage for free, and good prospects who bounce to a competitor that says "assessments from $X".

**Fix direction.** Even without fixed prices: a scope table (what an assessment includes, typical timeline, what changes the cost), a "free 15-minute triage" offer with a defined boundary, and a clear statement of what you will *not* take on. This also makes the FAQ answer "how much does it cost?" — currently absent.

### P1-4 · No verifiable credentials; About is mission/vision boilerplate

`about/` is 268 words, dominated by Mission / Vision / Work philosophy / six abstract values ("Integrity, Transparency, Professionalism…"). There is **no** certification, training provider, course, year started, number of cases, language ability, prior role, or platform-specific track record. The text also says *"I keep learning in web development, cybersecurity, automation, artificial intelligence and software engineering"* — which reads as student, not specialist.

**Impact.** For B2B due diligence (an agency handing over a Business Manager, or a brand with a 400k page), "who trained this person and what have they actually done" is the decision. The site answers neither. Note the tension: the prior audit correctly removed *unverifiable* claims ("300+ clients"), but removing them without replacing them with *verifiable* ones left a vacuum.

**Fix direction.** Replace philosophy with facts that can be checked: certifications (Google/Meta/Coursera/CompTIA/OSINT, whatever is real), a dated timeline, case counts you can document, languages (Bangla/English), hours and response SLA, and — where permitted — named clients with links. Each claim needs a source you can show on request.

### P1-5 · Case studies are the proof, but they are thin, undated and evidence-free

Word counts of the main content: Zero Idea **296**, Delicious Food **287**, UAE **249**, Dinajpur **239**, Santali **235**. Each has the right eight-part structure, but: no publication or resolution date, no `datePublished` in schema (documented as unknown), one duration metric total ("about two months"), **no redacted screenshots or Meta correspondence**, no "what you can verify" line, and the result sentence *"the page owner later shared a public video acknowledging the recovery"* — **the strongest single proof point on the site — is never linked or embedded.**

**Impact.** These are the only pages capable of converting a sceptical buyer, and they currently read as assertions. They are also the natural ranking assets for "Facebook page recovery case study" style queries and are too short to compete.

**Fix direction.** For each case: dates, platform, scale, duration, the exact blocker, what evidence was used, the outcome, and the limits (already good). Embed or link the public video with the owner's permission. Add a redacted screenshot where it proves something. Add `datePublished`/`dateModified` once dates are confirmed.

### P1-6 · The portfolio page undercuts the positioning

`/portfolio/` (133 words) leads with *"I build and maintain this website myself"*, lists *"Python (learning and automation)"* and *"AI-assisted development"*, and gives *SEO fundamentals / UI-UX fundamentals / Performance optimization* as "other skills". Its `<h1>` is "Technical work".

**Impact.** For a cybersecurity founder selling Meta recovery, this reads as a junior web-developer portfolio bolted onto the site, and "learning" is the last word a client wants next to their compromised Business Manager. It also has no ceiling: it invites comparison with developers rather than with security practices.

**Fix direction.** Either reframe it as "Tools I build for security work" (automation, OSINT workflows, audit tooling, this site as a case study in secure static delivery), or keep it strictly as a footer-level credibility footnote. Remove the word "learning" from public skill listings.

### P1-7 · Render-blocking, unminified, unfingerprinted CSS

| Metric | Value |
|---|---|
| Stylesheets | **5** separate files, all `<link>` in `<head>` (blocking) |
| CSS | 56 KB raw / **10.3 KB gzip** |
| JS | 11 KB raw / 3.8 KB gzip, both `defer` (good) |
| Homepage first load | **10 requests, ~104 KB gzip** before GTM |
| GTM/GA4 | typically **+120–160 KB and 3–6 requests** on top |
| Minification | none (HTML, CSS, JS all shipped with comments) |
| Fingerprinting | none — GH Pages serves `Cache-Control: max-age=600`, so revalidation every 10 min |

Five blocking round trips before first paint is the main device-independent bottleneck; on a 4G mobile connection that is ~2 extra RTTs versus a single stylesheet, and the inline critical-CSS path (hero only, ~2 KB) is unused.

**Fix direction.** Combine into one `site.css` (keeping the source split via a tiny build step, or concatenating at deploy), inline the above-the-fold rules, minify HTML/CSS/JS, and hash filenames. Fronting with Cloudflare gives brotli, long-lived immutable caching, and HTTP/3 for free. Keep the "no framework" constraint — this is a build step of a few dozen lines, not a rewrite.

### P1-8 · A security brand with no security posture

No `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy` or `Permissions-Policy`. No `/.well-known/security.txt`, no responsible-disclosure policy, no vulnerability-reporting address, no "how I handle your data" page.

**Impact.** Any technical buyer — an agency CTO, a security lead — will run this check in 30 seconds. For a *security* consultancy the absence is louder than for any other business. (GitHub Pages cannot set response headers, which is why this needs a proxy layer or, at minimum, `<meta http-equiv>` for the subset that works.)

**Fix direction.** Put Cloudflare in front (also fixes P0-5 redirects and P1-7 caching), then add HSTS, CSP, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`. Publish `/.well-known/security.txt` with a contact and an expiry — it is both a real control and a visible authority signal.

### P1-9 · Gmail as the primary contact, printed 55 times

`help.atikulislam@gmail.com` appears as a `mailto:` link **55 times** across the site (header note, trust band, footer, contact page, no-JS fallback, error message). No obfuscation, no role address on the domain.

**Impact.** (a) Authority: a security practice transacting from `@gmail.com` reads as a side project, not an agency. (b) Deliverability: form submissions relayed through Web3Forms to a Gmail inbox are a classic spam-folder pattern; there is no visible evidence of SPF/DKIM/DMARC on the domain. (c) Harvesting: 55 plaintext addresses is a scrape target.

**Fix direction.** Move to `help@atikulislam.me` (Cloudflare Email Routing is free) with SPF, DKIM and DMARC, keep Gmail as a forwarding target, and reduce the number of exposed mailto links to two (contact page + footer) with the rest routed through the form.

### P1-10 · Meta tags: the shell is complete but four tags are missing everywhere

Present and correct on all 21 pages: `canonical`, `og:type/site_name/title/description/url/image/width/height/alt/locale`, `twitter:card/title/description/image/image:alt`, `robots`, `theme-color`, `viewport`, `fb:app_id`.

Missing on **all 21** pages: `og:image:type` (all images are JPEG — declare `image/jpeg`), `twitter:site`, `twitter:creator` (or `twitter:site` = brand handle), and `author`. `404.html` correctly uses `noindex, nofollow`.

**Impact.** Small but real: some scrapers (LinkedIn/Slack previews) rely on `og:image:type`; the absence of `twitter:site` removes the attribution line from X cards.

### P1-11 · Mobile menu does not contain focus ◐

The mobile panel is a `<details>` element with `position: absolute`, no `role="dialog"`, no `inert`/`aria-hidden` on the rest of the page, and no focus trap. When open, keyboard users can tab straight into the content *behind* the panel, and screen-reader users can read the whole page while the "menu" is visually covering it. The trigger's accessible name stays "Menu" when open.

**Fix direction.** Mark the page content `inert` while the panel is open, keep focus inside the panel (or accept it as a non-modal disclosure and remove the visual overlay treatment), and swap the trigger label to "Close menu".

### P1-12 · iOS background scroll behind the open menu ◐

`main.js` toggles `.nav-locked { overflow: hidden; }` on `<html>`. On iOS Safari, `overflow: hidden` on the root element does not reliably stop the document from scrolling behind a fixed/absolute overlay; the classic symptom is the page drifting under the panel and the panel detaching from the header on rubber-band scroll.

**Fix direction.** Add the iOS-safe pattern (position-locked body with a stored scroll offset, or a fixed full-height panel with its own scroll container) and test on a real iPhone.

### P1-13 · The contact form cannot qualify or follow up

Fields: name, email, service select, message. Missing: platform, page/account URL or handle, when it started, urgency, current status (hacked vs disabled vs restricted), timezone, budget band, preferred channel, and a consent checkbox. No `maxlength` on the textarea. No thank-you page. The success panel replaces the form and offers WhatsApp only as an afterthought. `wa.me/8801300228105` has no pre-filled message.

**Impact.** Every enquiry needs a manual round-trip before you can judge it, which is exactly the triage cost that pricing and qualification normally remove. There is also no measurable "lead" event (P0-6) and no audit trail of consent (P0-4).

**Fix direction.** Add 3–4 qualifying fields (urgency, platform, page URL), a consent line linked to the privacy policy, a character cap, and a post-submit state that offers a calendar slot and a pre-filled WhatsApp link. Log the submit as a conversion.

## 6. P2 — Medium

**P2-1 · Above-the-fold image is lazy.** `index.html:62` — the header avatar `profile-96.webp` (visible at scroll 0 on every page) has `loading="lazy"`. It is small (2.7 KB) but it is in the first viewport, so lazy-loading delays rather than helps; there is no `fetchpriority="high"` anywhere. Fix: remove `lazy` from in-viewport images.

**P2-2 · No dates, and a sitemap that teaches Google to ignore `lastmod`.** `Article` nodes have no `datePublished`/`dateModified`, there are no `article:published_time` OG tags, and all **20 sitemap URLs share `lastmod` 2026-10-08**. Real per-URL dates (and `dateModified` when you revise a page) restore the freshness signal — important for a "recovery in 2026" query set.

**P2-3 · Duplicate boilerplate `FAQPage`.** The same three questions (guarantee / duration / what to send) are embedded in `FAQPage` markup on **6 service pages** and again on `/faq/`. Google has restricted FAQ rich results to authoritative government/health sites since 2023, so the upside is small and the duplication is noise. Keep `FAQPage` on `/faq/`, and give each service page its own 2–3 genuinely service-specific questions if you keep any.

**P2-4 · Titles are clean but generic.** All 20 end with "| Atikul Islam Rabbi"; none contains an intent modifier (hacked / disabled / locked / recovered / 2026) or geography. Examples: "Facebook Page Recovery | Atikul Islam Rabbi" (43 chars) vs. competing intent-rich titles. `contact/` is only 28 characters ("Contact | Atikul Islam Rabbi"). Descriptions are all unique and within 103–158 chars (good).

**P2-5 · `robots.txt` invites crawlers into internal folders.** It is `Allow: /` with a sitemap line — correct for the 20 real pages, but it also permits `/docs/`, `/prompts/`, `/scripts/`, `/design/`, `/data/` and `*.md`. Fix the publish scope (P0-1); add `Disallow` as a stopgap.

**P2-6 · Duplicated chrome.** The header is copy-pasted into 22 files (14 byte-variants, differing only by `aria-current`), the footer into 22 identical copies. That is **7.2 KB of shared markup per page and ~155 KB of duplicated source**, and it is why the earlier pass shipped 14 near-identical headers. `data/*.json` exists but is explicitly *not* the build source ("Proposal, not implemented" O8). Fix: a small HTML partial/include step at build time (compatible with the "no framework" rule).

**P2-7 · Desktop submenu without JS.** `.site-nav__sub-toggle` is only displayed when `.js` is present, so with JS disabled the mega-menu is hover-only — keyboard users cannot open it at all. Also, the toggle's visually-hidden label stays "Show services menu" after opening. Fix: always render the toggle, and flip the label on state change.

**P2-8 · Tablet measure.** `.grid--3` and `.grid--2` remain single-column until 1024 px / 640 px, and body copy has no `max-width`, so 768–1023 px viewports (iPad portrait) get ~700 px line lengths — the least readable width band on the site. Fix: add an intermediate 2-column step and a `max-width: 68ch` on prose.

**P2-9 · Schema is structurally good but under-populated.** `ProfessionalService` has no `address`, `telephone`, `email`, `priceRange`, `openingHours`, `sameAs` or `image`. `Person` has only `addressCountry: "BD"` and no `email`/`telephone`/`hasCredential`/`alumniOf`/`award`. `Organization.url` points at the personal site rather than a company page. With a GBP available (P1-2), these fields are how the entity becomes corroborated.

**P2-10 · Dead weight in `assets/`.** `assets/source/profile-original-512.png` (369 KB, unreferenced) is publicly downloadable — the original photo, published for no reason. `assets/brand/favicon.ico` is byte-identical to `/favicon.ico` (md5 match). Sprite defines **26** icons, uses **24** (`i-arrow-up-right`, `i-circle-check` unused). Fix: delete or move outside the publish tree; optionally trim the sprite.

**P2-11 · Client-side-only form guards.** `novalidate` disables native validation and the whole form is `.js-only` (hidden without JS). Validation, the honeypot and the 15 s timeout all run in the browser; nothing enforces a size cap on the textarea, and there is no evidence of rate limiting on the Web3Forms endpoint. Acceptable for a brochure site, but the failure modes (spam flood, oversized payload, silent delivery failure) are all invisible to you today.

## 7. P3 — Low / polish

- **P3-1** GTM's inline snippet sits at `head[4]`, **before `<title>` and all meta tags**. Move it after the charset/title/meta block so the parser can publish the title and description first.
- **P3-2** No `preconnect`/`dns-prefetch` for `googletagmanager.com`, so GTM pays a fresh DNS+TLS on the critical path. (Fonts are self-hosted and correctly preloaded — keep that.)
- **P3-3** Sticky header combines `backdrop-filter`, a scroll listener and a reveal `IntersectionObserver`. `backdrop-filter` is among the most expensive compositing effects on mid-range Android; consider dropping it below 1024 px.
- **P3-4** Profile links (LinkedIn, GitHub, Upwork, Facebook, Instagram) have no `rel="me"`, so the site does not formally assert identity ownership.
- **P3-5** `site.webmanifest` lacks `id`, `lang`, `dir`, a `maskable` icon purpose, `screenshots` and `shortcuts`; no `apple-mobile-web-app-title`.
- **P3-6** The TLS certificate covers `www.atikulislam.me`; confirm it 301s to the apex rather than serving a duplicate (the canonical tag mitigates, a redirect is cleaner).
- **P3-7** The 404 page is well built (33 links, `noindex`) but offers no search and no explanation specifically for `/blog/` or legacy paths.
- **P3-8** Documentation drift: `README.md` and `docs/audit-2026.md` claim "one consistent `@graph` per page" (there is none) and that the checker validates "JSON-LD" (it validates only that it parses). `docs/audit-2026.md` also still describes the site as verified when P0-1/P0-2/P1-1 contradict it.
